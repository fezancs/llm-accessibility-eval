| 2026-11-14 | **Analysis reporting clarifications (SPEC 10; no metric definition changed).** (1) A statistic whose data come from fewer than 2 bootstrap clusters (DCDI, S_C3, S_C5, the DCDI decomposition, pressure, intent, end-of-session regression; with one E2 run a cluster is one step) gets no CI, since its percentile interval would be [est, est]; its replicates are kept, and a composite of it (S6, CCS) gets no CI either. Table III then prints the bare estimate and values.tex has no `-ci/-lo/-hi` keys for it. (2) E3c: if the generators are not connected through the non-recused comparisons (for example a one-judge file), theta, S_C4 and eta are reported as not identified instead of the ridge's 0 (S_C4 = 0.5). | 2026-11-14 | **E2 harness fixes before the first E2 call** (from an independent code review). (1) `e2_agent.run_turn`: a response that stops with finish "length" when prompt plus output fill the model's window, with the prompt at least half the window, is context exhaustion. Its truncated output is neither executed nor kept, and the run ends (SPEC 6.1). llama.cpp with `--no-context-shift` signals a full window this way instead of rejecting the request, so before this fix a full window would have produced empty "ok" steps up to position 24. A max_tokens stop on a short prompt stays an empty response (SPEC 13.3a). (2) `e2_run`: a padded control runs only for a session step that completed (an exhausted step is never scored). (3) `chat_adapter`: tool-call arguments that are not valid JSON (or are empty) are replayed as `{}`; llama.cpp b12004 otherwise answers HTTP 500 for the whole conversation. The call itself is still counted as malformed and answered with an error. (4) `run_local.sh`: a pilot that did not finish or made no tool call no longer counts as a SPEC 12 exclusion. | Found before E2 ran; each was reproduced offline against the llama.cpp b12004 behaviour. | Changes which E2 steps are scored relative to the unfixed code, in the direction SPEC 6.1 prescribes. No metric, prompt or task changed. |

| 2026-11-13 | **Vision-encoder warm-up, restart on encoder failure, and a step gate on failed requests** (`local/run_local.sh`, `local/step_errors.py`). In the re-run, Qwen2.5-VL 7B's vision encoder failed one allocation at 22:45 (`vk::CommandBuffer::end: ErrorOutOfDeviceMemory`, during a 1597x1198 image); from then on every image request failed ("failed to process mtmd chunk") while `/health` stayed ok. About 1.3 GB of VRAM is left next to this profile and the desktop; the same image works as the first request after a fresh start, so the failure depends on what else holds VRAM at that moment. The pipeline was stopped at 22:52 before any step was marked done. Now (1) after launching a vision profile the script sends seven large E3 images of different shapes and one small one (live, uncached, not logged), so the encoder allocates its buffers while memory is free; (2) the watchdog restarts a server whose log shows a vision-encoder failure since its launch; (3) a step is marked done only if its command exits 0 and no request made during the pass ended in failure (context exhaustion excepted); API steps get up to four passes, each retrying only failed requests. | The harness scripts record failed requests and exit 0, so the exit code had twice marked steps done that ran against a broken server. | None on scores: no model setting changed, failed attempts are never cached, and every request is still answered by the same model and flags.
